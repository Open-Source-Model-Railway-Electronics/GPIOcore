GPIOcore serial protocol

Date: 2026-11-18 (updated) · Status: pre-release (v0). This document describes the current protocol, as implemented by the firmware (software/GPIOcore), the Qt GUI and the simulator (software/gui/src/simulateddevice.cpp).

After opening the port the GUI sends HELLO. A board that answers is a GPIOcore decoder and reports its capabilities. If a board does not answer at all, the GUI first waits up to 30 s for the board to announce itself (a short press on its config button, §3.1). If nothing comes, the GUI asks you to flash the GPIOcore firmware.

1. Framing

<command> <payload ...> <checksum>
command  : high nibble = message group, low nibble = payload length (0..14)
           low nibble 0xF = extended length: payload[0] = length incl. itself (max 32)
checksum : XOR of command and all payload bytes
ExceptionBytesRemark
ACK701 byte, no checksum
NACK71 <reason>2 bytes, no checksum (1 = checksum, 2 = length, 3 = timeout)
Host → device with length 0<cmd>Executed immediately and gets no checksum and no ACK (REQ_VERSION, HELLO)

The protocol is binary with full 8-bit bytes. So there is no 7-bit limit as in LocoNet. The "bit 7 = state, bits 0–6 = id" layout is not used anywhere.

Every complete frame with a valid checksum gets one ACK from Transceiver::receive() after it has been processed. A GET first gets the data reply and then that ACK.

Timing and limits (src/Transceiver.cpp):

  • Byte timeout. At most 5 ms may pass between two bytes of one frame. After that the firmware answers with NACK 3 and starts over. So send a frame in one go.
  • Maximum length. A payload is at most 32 bytes; longer gives NACK 2.
  • Start-up. After a reset the firmware sends nothing: without the GUI the board is silent. After about 2.5 s the GUI asks for REQ_VERSION and then reports in with HELLO (within the serial window of 5 s, §3.1). If no HELLO arrives, the firmware stops Serial and D0/D1 become normal pins. Opening the port resets an Uno or Nano through DTR. The bootloader and setup() together take about 1–2 s.
  • Index ≥ 16. An index of 16 or higher is ignored, but the frame still gets an ACK. A GET then gives no data reply.
  • Saving. SET_INPUT_DATA and SET_OUTPUT_DATA go straight to EEPROM. A SET_OUTPUT_DATA executes the state once, even if it has not changed (this is how "Test state" works).

Block signal (type 15). The firmware chooses the aspect itself from two inputs, normally sensors (input type 4), every 50 ms (blockSignals() in GPIOcore.ino): data[0] if the own block input is occupied, otherwise data[1] if there is a next block and its input is occupied, otherwise data[2]. "Occupied" = the input is in use, has a pin and is pressed (LOW, or the analog condition holds); one input may serve several signals. The current aspect is only kept in RAM (no EEPROM writes) and reported as OUTPUT_EVENT state 2 when it changes; GET_OUTPUT_STATE answers state 2 + the current aspect. Flashing lamps flash at a fixed 1 Hz. Commands to it are ignored: inputs (toggle / absolute, own values), route steps and DCC-ext.

Example: own block = input 3, next block = input 9, occupied = lamp C (0x04), next occupied = lamp B (0x02), free = lamp A (0x01): data = 04 02 01 93. Without a next block (own = 5): data[3] = 0x55.

Until 2026-11-16 this was a mode of the 4-aspect signal (type 10, data[3] bit7, with lamp numbers in data[2]/data[3]). That mode is removed: type 10 is a manual signal again, and the GUI loads such a signal from an old board file as a manual signal (data[2] = data[3] = 0).

**Servo as semaphore arm (type 11, data[3] bit7).** The servo follows input data[3] & 0x0F: occupied → state 0 (curved = arm at stop), free → state 1 (straight = clear); bit6 swaps them. It moves at its own speed through the normal state change (and reports it like any state change); checked every 50 ms.

Sound effect (type 14, HELLO bit4). A DFPlayer Mini has its RX connected to the TX pin D1 of the Nano (through 1 kΩ). The firmware sends the DFPlayer frame (9600 baud, 10 bytes: 7E FF 06 12 00 00 track csH csL EF: play /MP3/<track>.mp3 by name, e.g. /MP3/0001.mp3; 16 instead of 12 = stop) only if no PC is connected: in a configuration session D1 is the USB line. Every time a track is started (or stopped), the output reports OUTPUT_EVENT with state 2, value = track, even if it could not play anything. Several sound outputs may share D1 (the GUI does not count that as a conflict); D1 together with another input or output is a conflict.

PWM pins are D3, D5, D6, D9, D10 and D11. D9/D10 do no PWM as long as a servo output exists (Servo library, timer 1).

Routes are not part of SET_INPUT_DATA; they only travel through GET_ROUTE / SET_ROUTE (§4). GET_INPUT_DATA returns the same 14-byte layout.

Analog inputs (HELLO bit4). Instead of a pin number, pin then contains 0x20 | mode << 3 | channel: channel 0–7 = A0–A7 (the real pin is 14 + channel), mode 0 = below the threshold, 1 = above the threshold, 2 = at the threshold (one button of a resistor ladder). Mode 3 (so also 0x3F = not used) is never analog. The threshold (0–1016, steps of 8) is in b6 as threshold / 4: SET_INPUT_DATA takes it from there, GET_INPUT_DATA puts it back there (only for an analog input; otherwise b6 is 0xFF). The firmware stores threshold / 8 (7 bits, EEPROM.md).

The firmware reads every 50 ms and counts a change only after two equal readings. "Pressed" works exactly like a button to GND (LOW): toggle switches when pressed, absolute follows (pressed = 0), all three route types start when pressed. The rules of the real pin apply to the channel (A7 = config button, A6 only on the Nano) and an analog code as an output gives NACK 5. Several analog inputs may share one channel (resistor ladder); a digital input or an output on that pin is a conflict.

Input types:

  • 0 toggle — switches when the button is pressed (falling edge) or on every DCC command;
  • 1 absolute — follows the level (closed = 0) or the DCC direction;
  • 2 route — starts when the button is pressed (falling edge) or on every DCC command for the address, direction 0 and 1;
  • 3 not in use;
  • 4 sensor — an occupancy detector or other sensor (digital pin or analog condition). It switches nothing itself and has no output, route or DCC address; it only provides its state (pressed = LOW = occupied) for block signals and servos used as semaphore arms (§2.1). Until 2026-11-16 type 4 was the recorder: the GUI loads a "recorder" input from an old file as 3; on a board an old recorder input now reads as a sensor (harmless, it switches nothing);
  • 5 — reserved (was the recorder's feedback input, removed 2026-11-16); the firmware reads it as 3.
  • 6 route straight only — starts when the button is pressed, or only on a DCC command 'straight' (direction 1) for the address;
  • 7 route curved only — same, only on 'curved' (direction 0).

With 6 and 7 two routes share one DCC address, for example a level crossing barrier: curved = closed, straight = open.

Repeated DCC packets. A command station sends a turnout command a few times. A toggle input and a route take the first one and ignore the same address for 500 ms afterwards (DCC_LOCKOUT_MS). An absolute input does not need this (same direction = same state). SET_INPUT_STATE (0x32) goes through the same code, so the lockout time applies there too.

Start-up (firmware 2026-11-18). The first sample of an input's pin is its starting level, not an edge. An absolute input applies that level once, exactly as an edge would (custom values included), but only when it differs from its output's stored state: a switch moved while the power was off is followed, without needless EEPROM writes. Toggle and route inputs do nothing at start-up. SET_INPUT_DATA starts an input again (the next sample is a new starting level), so a new configuration gets the same rule. An input on D0/D1 starts when those pins become I/O (serialToIO()).

2.3 Presets (in the GUI)

Since 2026-11-13 the presets are no longer in the firmware (that saved 2.7 KB of flash). The GUI calculates a preset (presetBoard() in gpioconfig.cpp) and sends the result as normal SET_OUTPUT_DATA / SET_INPUT_DATA (saved live). So this also works offline and in the simulation.

3. HELLO — logging in and configuration session

host   -> 90
device -> 95 <protocol> <max steps per route> <step pool lo> <step pool hi> <flags>
protocol: protocol number, currently 2
flags  : bit0 = D0/D1 usable as I/O outside a config session
         bit1 = SERVO_LIVE supported
         bit2 = (no longer sent; was: recorder in external EEPROM)
         bit3 = BOARD settings (C0 / CF) supported, see section 9
         bit4 = analog inputs (GET_ANALOG D1 / D3) and the sound effect output (type 14)
         bit5 = Bluetooth: BT_SETUP (E0 / E3) and the announce after a short press on the
                config button (GUI mode, section 3.1)
step pool: number of route steps that still fit with the current board settings
           (timing on/off), all routes together

The GUI sends HELLO right after the boot message (version). That is about 1.5 s after the reset that opening the port causes through DTR. For boards without auto-reset it sends it after REQ_VERSION.

What the decoder does (proposal, so that D0/D1 become usable):

  1. After power-up or reset it waits 5 s with Serial active and does nothing yet on D0/D1.
  2. If a HELLO arrives within those 5 s, there is a configuration session: D0/D1 stay Serial until the next reset. Outputs and inputs on D0/D1 do nothing in that session.
  3. If no HELLO arrives and the configuration uses D0/D1, it does Serial.end() and sets D0/D1 as normal I/O (pinMode according to the configuration). Otherwise Serial stays open (§3.1).
  4. If you want to configure again later, you reset the board. The GUI does this itself when connecting (DTR). Without a reset (over Bluetooth, or a USB chip without DTR): press the config button briefly (§3.1).

Is using D0/D1 sensible at all? It can be done, with three caveats:

  • On an Uno/Nano, D0/D1 are connected to the USB-serial chip through 1 kΩ. An output simply works. An input with a button to GND works too, because the button wins over the 1 kΩ.
  • A heavy load or a low-impedance circuit on D0 (RX) can disturb uploading firmware. Preferably use them for LEDs, or for relays through a transistor.
  • They do not work during a configuration session. A "Test state" on an output on D0/D1 then does nothing.
  • In the simulator (the firmware built for the PC, GPIOCORE_HOST, serialPinsFree() in config.h) D0/D1 are always normal pins: the GUI does not talk to it over D0/D1.

The GUI lets you choose D0/D1 if the decoder reports bit0, and offline. It then shows a note (not an error). Without bit0 they are reserved and red.

3.1 Serial window, GUI mode and the announce (HELLO bit5, firmware 2026-11-18)

The 5 s at start-up are the serial window: it runs from serialWindowStart (0 at start-up). Without HELLO in the window the firmware does Serial.end() and D0/D1 become I/O (serialToIO(); a sound effect output gets TX at 9600 baud for the DFPlayer) — only when the configuration uses D0 or D1 (firmware 2026-11-18): an input pin, an output or frog relay pin, or a sound effect output (TX). Otherwise Serial stays open at 115200 for good, so a GUI can connect at any time (USB without a reset, Bluetooth) without a press on the config button. serialCheck() decides this every 50 ms after the window, outside a session: a configuration that starts using D0/D1 later (e.g. in the simulator) closes the port then. A session keeps the port open until the next reset, as before (the board does not notice the GUI going away); the next start-up decides again.

GUI mode. A short press on the config button (A7, Nano) outside config mode:

  • serial port closed (serialIsIO): Serial.begin(115200) again, D0/D1 are Serial (what is on them pauses, as in a session), and a new 5 s window starts (serialWindowStart = millis());
  • serial port open, no session yet (start-up window): the window starts again;
  • always: the board sends the announce, the HELLO reply (95 ...) unasked. It does not start a session.

The GUI then sends REQ_VERSION and HELLO as usual; with HELLO the session starts and the port stays open. Without HELLO within 5 s, D0/D1 become I/O again (when the configuration uses them), exactly as after start-up.

The GUI. When it gets no answer to REQ_VERSION or HELLO while connecting, it does not give up: it shows "Waiting for the board — press its config button briefly (Nano)…" and listens for up to 30 s (DeviceLink::announceWaitMs) for the announce. Then it continues with REQ_VERSION and HELLO. After 30 s it shows the "No GPIOcore board answered" message. Disconnect cancels the wait. This is what you need over Bluetooth: opening a Bluetooth COM port does not reset the board, so after 5 s its serial port is closed (when the configuration uses D0/D1).

4. Routes

Step = 4 bytes

byte 0 : bits 0-3 output id (0-15) | bit 4 raw value | bit 5 STEP_VALUES (custom value) | bits 6-7 reserved (0)
byte 1 : value   raw = 0: state 0 = curved, 1 = straight
                 raw = 1: aspect 0-255 (signal), angle 10-170 (servo), PWM 0-255, track 0-255 (sound, 0 = stop)
byte 2 : wait time bits 0-7
byte 3 : bits 0-5 = wait time bits 8-13 | bits 6-7 reserved (0)
wait   : 14 bits of 0.1 s = 0 .. 1638.3 s (~27 min), time after this step before the next one

Example: output 13, aspect 200, wait time 1638.3 s → 1D C8 FF 3F.

  • The GUI chooses the value kind per output type. Turnouts, lights and relays get curved/straight. A 4-aspect signal gets an aspect number. A servo gets curved/straight or an angle, and may occur several times in one route (intermediate positions). PWM gets a value.
  • New steps get a 0.3 s wait time.
  • Timing off (board setting, §9): on the wire a step stays 4 bytes, but the decoder stores only byte 0 and 1 (2 B per step) and after each step waits the fixed delay from the board settings. When read back, byte 2 and 3 are 0. The GUI hides the wait time column.
  • The decoder executes a step like this: 
// raw == 0 -> like a DCC command:   callbackInput( id, value, 0 )
// raw == 1 -> signal / PWM:         output[id].setVal( value )
//             servo:                output[id].setPosition( value )   // new, moves to this angle
// then wait 'delay' x 100 ms before the next step

Own values of a toggle or absolute input (firmware 2026-11-14)

A direct input (toggle or absolute) may have exactly 2 steps in its own route slot (same index, GET/SET_ROUTE), both with **bit 5 = STEP_VALUES (0x20)** in byte 0. Step 0 applies when the state of the input becomes 0 (off / curved), step 1 when it becomes 1 (on / straight). Each step works like a route step: raw = 0 sets curved / straight, raw = 1 sends an angle, aspect, PWM value or track. The output id of the step is used (the GUI puts the outputID of the input there); the wait time does not count.

  • This applies to the button, the analog condition and normal DCC accessory commands on the address of the input. DCC-extended still passes its value straight through.
  • Without those 2 marked steps (another number, or steps without 0x20), the input works as always: the state goes to the output.
  • For a direct input without own values the GUI sends an empty route, so that the slot is empty. The 2 steps count towards the route pool. In the board file they are stored as "values": [ {value, raw}, {value, raw} ].

Transfer in pieces of at most 7 steps

GET_ROUTE  82 <route> <first>
SET_ROUTE  8F <len = 4 + 4n> <route> <total> <first> <step ...>     (also the reply to GET_ROUTE)
  • A route of 16 steps goes in three messages: 7 + 7 + 2. An empty route is one message with total = 0.
  • With first = 0 the decoder starts the route again. It saves the route as soon as total steps have arrived.
  • Per input the GUI writes: SET_INPUT_DATA, then SET_ROUTE(s), and then reads back the input and route.

5. SERVO_LIVE

A2 <output> <angle> moves the servo to angle immediately. Nothing is saved and the state machine does not change.

  • The GUI sends this while you drag a servo slider, if the Live checkbox is on. A fast series of slider values is merged into only the last one.
  • Proposal for the decoder: attach the servo, write the angle, and detach after about 1 s without a new SERVO_LIVE.

6. EEPROM budget

See **EEPROM.md**: the layout, what fits in 1024 B, and what can still be compressed. In short: an input is 4 B, the routes have a pool of 762 B to themselves, and with timing off 16 × 16 steps fit internally (512 B).

8. Decoder firmware

The details are in EEPROM.md and in the commits of software/GPIOcore. In short: HELLO with boot window, board settings (§9), route pool with dynamic allocation, per-step timing, interlocking, SERVO_LIVE and setPosition(), A6/A7 as analog input, and protecting pin 2.

Pin 2 (DCC input), D13 (config LED) and A7 (config button) must never be used as input or output. A SET_INPUT_DATA or SET_OUTPUT_DATA with pin 2 gets NACK 5 (invalid pin) and is not saved. The same applies to D0/D1 as long as the decoder does not report bit0 in HELLO, and to A6/A7 as output or on a board other than the Nano.

9. Board settings and name

host   -> C0                                        (GET_BOARD, no payload)
device -> CF <len> <type> <flags> <delay> <name ...> (also SET_BOARD from host -> ACK)
len    : 4 + name length (name 0..16 ASCII bytes, no terminator)
type   : 0 = Arduino Uno (no longer offered: the GUI reads it as a Nano), 1 = Arduino Nano, 2 = DCCnext,
         3 = Jack of all trades
flags  : bit0   = reserved (was: recorder enabled), ignored and cleared
         bit1   = route step timing (per-step wait times stored)
         bit2-3 = route interlocking: 0 = off (all routes may run in parallel)
                                      1 = on  (one route at a time)
                                      2 = auto (routes that move a turnout run one at a time,
                                                other routes run in parallel)  <- default
delay  : fixed wait after each route step when timing is off, x 0.1 s (default 3 = 0.3 s)
  • Name. The name identifies the board. The GUI keeps a file <name>.json per board (names of inputs and outputs plus all settings). When connecting it reads HELLO, then GET_BOARD, loads <name>.json if it exists, and then reads everything from the board. What the board says wins; the names come from the file. A new board has an empty name; the GUI then asks for one.
  • Type. Determines which pins exist. On the Nano, A6/A7 (pin index 20/21) are analog-only inputs without pull-up: the firmware reads them with analogRead() < 512 as "pressed", and the button needs an external 10 kΩ pull-up. The type is set by the GUI; the firmware only uses it to check pins. Type 0 (Uno) is no longer offered: the GUI shows it as a Nano and the firmware applies the Nano's pin rules to it.
  • Recorder. Removed on 2026-11-16 (it needed an external I2C EEPROM on A4/A5, ±4.6 KB flash and ±250 B RAM). A4/A5 are always normal pins.
  • Switching timing on/off. The decoder converts the stored routes (2 ↔ 4 B per step). If it does not fit (timing on with too many steps), the answer is NACK 4 and the old setting stays.
  • Interlocking. A route that is refused by interlocking is ignored (not put in a queue): this protects against a wrong button press. "Moving a turnout" = the route contains an output of type servo, single pulse or double pulse.
  • NACK reasons: 1 checksum, 2 too long, 3 timeout, 4 full (pool or route), 5 invalid pin.

9.1 How the firmware does it (2026-11-12, deviations and choices)

  • Default values new board: Nano, timing off, interlocking auto, delay 0.3 s. A board without the magic 'G', '2' (EEPROM.md) gets these values.
  • SET_ROUTE writes immediately. first = 0 makes the route its new length at once (the routes behind it shift up, NACK 4 if it does not fit); every following piece is written directly. An interrupted transfer therefore leaves a half-written route behind. The GUI always reads the route back afterwards.
  • Switching timing on gives every existing step the board delay as wait time. The first step starts immediately. Wait times run down on the 50 ms tick of the inputs.
  • Interlocking: a route counts as running until the wait time after the last step has passed.
  • Still open: setPosition()/SERVO_LIVE do not switch the unifrog relay; SET_OUTPUT_DATA does not set pinMode for newly configured pins; an output on D0/D1 is not stopped during the serial window.

10. Config button (A7), config LED (D13) and teaching servos (firmware, 2026-11-13)

  • A7 = config button: push button to GND, with an external 10 kΩ pull-up to 5 V (A7 has no internal pull-up). The firmware reads it with analogRead() with hysteresis: pressed below 200, released above 800.
  • D13 = LED: on = normal, flashing = config mode.
  • An output or input that uses D13 or A7 is set to not in use at start-up; SET_*_DATA with D13/A7 gets NACK 5.

11. Bluetooth (HC-05, HELLO bit5, firmware 2026-11-18)

An HC-05 on D0/D1 replaces the USB cable. The GUI's Board > Set up Bluetooth (HC-05) sets it up through the board.

Wiring (HC-05 → Nano): VCC → 5 V, GND → GND, RXD → D1 through a voltage divider (1 kΩ from D1 to RXD, 2 kΩ from RXD to GND: the HC-05 takes 3.3 V), TXD → D0 through a Schottky diode (BAT85 or 1N5819) with the cathode at the HC-05 TXD. The diode can only pull D0 low, so the USB-serial chip still drives D0 and USB keeps working while the HC-05 is attached.

**BT_SETUP (E0). The HC-05 must be in AT mode**: hold its button while it gets power (LED blinks slowly, about every 2 s); AT mode is always 38400 baud. The handler only sets btSetupPending; loop() then runs btSetup(), which blocks for up to ~2 s:

  1. Serial.flush(); for each baud rate 38400, 9600, 57600, 115200, 19200: Serial.begin(baud), empty the input, send AT\r\n, wait up to 300 ms for OK.
  2. Found: AT+UART=115200,0,0\r\n (wait for OK), then AT+NAME=GPIOcore\r\n, or AT+NAME=GPIOcore-<name>\r\n with the board name (only letters, digits, - and _, max. 20 characters in total). The PIN is not changed.
  3. Serial.begin(115200), empty the input, send BT_RESULT (E3 status baud÷2400 name_ok).

Meanwhile the PC gets the AT commands at the wrong baud rate (noise) and maybe NACKs caused by the HC-05's answers. The GUI sends nothing else during the set-up (one task, 8 s timeout) and ignores every byte until it finds a valid BT_RESULT frame in the byte stream. The session goes on at 115200 afterwards.

Afterwards: unplug the board and plug it in again (without holding the HC-05 button); the HC-05 now runs at 115200 baud. Pair GPIOcore… in Windows Bluetooth settings (PIN 1234, or 0000 on some modules); Windows creates a COM port for it. Connecting over that port does not reset the board: press the config button briefly (§3.1).

Simulator. gpiocore_fw_host can attach a fake HC-05 (frame 'H' <baud÷2400>) that answers OK to every AT command at that baud rate and reports what it received ('h'); bytes the firmware sends at a baud rate other than 115200 (and 9600, the DFPlayer) reach the GUI as noise (F0 per byte), never as valid frames.
